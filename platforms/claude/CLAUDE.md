# 全局规则

## CI 与耗时检查

- 运行完整 CI（例如 `npm run ci`、`tools/ci.mjs`）或其他耗时很长的完整检查之前，必须先征得用户同意。
- 适用于所有项目、所有阶段，包括迭代过程中、推送、开 PR、合并之前。项目文档（如 AGENTS.md、CONTRIBUTING.md）要求开 PR 前跑 CI 时，也要先问。
- 需要跑时，说明原因和预计耗时，然后提问；得到明确同意后才运行。
- 平时只跑与改动相关的检查：改动文件对应的测试、改动文件的 lint，以及可能影响默认行为时的快速回归检查。
- 没跑完整 CI 就推送或开 PR 时，在 PR 描述里写明"尚未运行完整 CI"。

## Karpathy Guidelines：每次任务遵循

适用于所有任务；编程、研究、配置、文件操作和写作均遵循以下四条原则。简单任务直接完成，复杂任务采用与工作量相称的计划和验证。
来源：https://github.com/multica-ai/andrej-karpathy-skills/blob/main/skills/karpathy-guidelines/SKILL.md

### 1. 行动前想清楚（Think Before Coding / Acting）
- 先理解目标、现有上下文和约束；指出会影响结果的关键假设，不把猜测当作事实。
- 存在会实质影响结果的歧义或缺失信息时，明确指出并提问；信息足够时直接推进。
- 有更简单的可行方案时，说明判断和取舍；发现要求存在问题时，给出具体理由和建议。

### 2. 简单优先（Simplicity First）
- 用满足当前需求的最小实现或行动解决问题，不擅自增加功能、文件、步骤或配置项。
- 不为一次性需求建立复杂抽象，不为未提出的未来需求设计扩展机制。
- 根据真实输入和环境处理错误，不堆砌无实际依据的防御逻辑；发现不必要的复杂度时简化。

### 3. 精准修改（Surgical Changes）
- 每项修改都应能追溯到当前任务；遵循现有代码、文档和配置的风格。
- 不顺手重构、重排格式或修改无关内容；发现无关问题时，必要时说明，不擅自处理。
- 清理由本次修改造成的无用导入、变量、函数或临时文件；保留用户已有改动。

### 4. 以可验证的目标推进（Goal-Driven Execution）
- 开始执行前明确完成标准；多步骤任务给出简短计划，并为关键步骤确定验证方式。
- 修复问题时，先复现或确认原因，再验证修复；重构时，验证前后行为符合要求；配置变更后回读或检查实际状态。
- 根据影响选择必要验证；低影响、可逆的简单修改可用直接检查，不机械添加测试或重复验证。
- 持续推进到完成标准满足；完成报告区分已验证结果与尚未验证的内容，不把工具调用成功等同于任务完成。
